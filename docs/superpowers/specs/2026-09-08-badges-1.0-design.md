# markdown-badges 1.0 design

Status: approved, not yet implemented. Date: 2026-09-08. Branch: `redesign-1.0`, based on `review-fixes`.

## Problem

`markdown-priority-badges` 0.2.0 models everything as a ranked severity level. One config option, `levels`, is a name to colour map, and `priority_of` ranks a name by its position in that map. The badge catalogue added on `review-fixes` exposed the flaw: a status badge such as `!wip` and a branding badge such as `!github` have to be declared in `levels` to work, so `priority_of` will happily report `!github` as a severity ranked between two real priorities. The name of the package promises a priority tool, and the config gives no way to say "this badge is not a priority".

The catalogue also lives only in `scripts/gen_badges.py`, a build-time script. A user gets nothing out of the box beyond the four built-in levels, and must paste a wall of TOML to use any catalogue badge.

## Decisions

These were settled before this document was written.

1. **Clean break at 1.0.** `levels` is removed rather than deprecated. Badges are declared under a type-keyed `badges` option.
2. **Rename to `markdown-badges`.** The PyPI name is free. Import path becomes `markdown_badges`, config key becomes `markdown_badges`. Users migrate once, in one release, rather than twice.
3. **The `!` / `!!` shorthand is not built in.** It becomes an entry in a config-driven `shorthand` map, so a user can restore it in three lines or invent their own markers.
4. **The catalogue ships in the package and every group is active by default.** A user who installs the package and enables the extension gets all catalogue badges with no further config. The `catalogue` option narrows that.

## Config surface

```toml
[project.markdown_extensions.markdown_badges]
catalogue = ["priority", "status", "branding"]   # default: all three; [] disables the catalogue

[project.markdown_extensions.markdown_badges.badges.priority]
blocker = "#7b1fa2"          # a new priority badge, ranked after the catalogue ones
critical = "#8e0000"         # an existing catalogue name: recolours it, keeping its rank

[project.markdown_extensions.markdown_badges.badges.branding]
jira = "#0052cc;background-image:url('data:image/svg+xml,…');padding-left:1.75em"

[project.markdown_extensions.markdown_badges.shorthand]
"!"  = "high"
"!!" = "critical"
```

Plain Python-Markdown takes the same three options as keyword arguments, with `badges` as a nested dict keyed by type name.

## Package layout

The current single 300-line `__init__.py` is split. Each module has one job and can be read on its own.

| Module | Responsibility |
| --- | --- |
| `catalogue.py` | `BadgeType`, `Badge`, `ICONS`, `claude_burst`, and the `CATALOGUE` tuple. The only place badge data lives. No Markdown imports. |
| `styling.py` | `_to_hex6`, `_text_color`, `_badge_element`, `_badge_html`, `_BADGE_STYLE`. Colour maths and span construction. |
| `parsing.py` | `_inline_re`, `BadgeInlineProcessor`, `ShorthandTreeprocessor`, `priority_of`, `rank_of`, `badges_in`. |
| `__init__.py` | `MarkdownBadgesExtension`, config resolution, `makeExtension`, and the public re-exports. |

`py.typed` stays. The wheel ships `markdown_badges/` only; `scripts/` and `docs/` stay out.

## Data model

```python
class BadgeType(Enum):
    PRIORITY = "priority"
    STATUS = "status"
    BRANDING = "branding"


@dataclass(frozen=True)
class Badge:
    name: str
    value: str          # CSS background-color, optionally followed by more declarations
    type: BadgeType
    note: str = ""
```

`CATALOGUE: tuple[Badge, ...]` holds the 18 badges already written on `review-fixes`, in the order they appear there. Order inside `BadgeType.PRIORITY` is the severity order, ascending.

`value` keeps the extended-CSS behaviour shipped on `review-fixes`: it is written into the badge's `style` attribute as the `background-color`, and anything after a `;` becomes a further declaration. Only its type is validated.

## Resolution

Resolution happens once, in `extendMarkdown`, and produces a `dict[str, Badge]` keyed by name.

1. Start with the catalogue filtered to the types named in `catalogue`. Preserve `CATALOGUE` order.
2. For each type block in the user's `badges`, walk the entries in config order. A name already present is replaced in place, keeping its position and type. A new name is appended to the end of its type's run.
3. The result is the resolved map. The inline pattern is built from its keys, longest name first so no name shadows a longer one.

Rank is position within the resolved `PRIORITY` badges. An override therefore never reorders anything, and a user adding `blocker` gets a rank above `critical` because it is appended after it.

## Public API

```python
from markdown_badges import (
    Badge, BadgeType, CATALOGUE,
    catalogue_for, badges_in, priority_of, rank_of,
    MarkdownBadgesExtension, makeExtension,
)
```

In every signature below, `badges` is a resolved `Mapping[str, Badge]`, the same shape `catalogue_for` returns and the same shape the extension builds internally. It defaults to the full catalogue when omitted. This replaces the 0.2.0 convention of passing a bare sequence of level names, so a caller now passes badge objects rather than strings and no longer needs a separate ordered list to express rank.

- `catalogue_for(*types: BadgeType) -> dict[str, Badge]` returns the catalogue subset, in catalogue order. No arguments means every type.
- `priority_of(text, badges=None) -> str | None` returns the highest-ranked `PRIORITY` badge name found in `text`, or `None`. Non-priority badges are ignored entirely.
- `rank_of(name, badges=None) -> int` returns the severity rank among the `PRIORITY` badges of `badges`, or `-1` when the name is absent or is not a priority badge.
- `badges_in(text, badges=None) -> list[Badge]` returns every badge found, of any type, in the order they appear in `text`. This is what a dashboard wants when it needs the status and the repo host as well as the priority.

`priority_of` and `badges_in` remain plain-text scans, not Markdown parses. A keyword inside a code span or escaped as `\!high` still counts. This limit is already documented and stays documented.

Removed: `LEVELS`, `DEFAULT_LEVELS`, `level_rank`, `PriorityBadgesExtension`, `PriorityInlineProcessor`, `TasklistShorthandTreeprocessor`, `MARKER_RE`.

## Shorthand

`shorthand` maps a literal marker to a badge name. The treeprocessor keeps its current position, priority 26, above `pymdownx.tasklist` at 25, so it still sees pristine `[ ] <marker> text`.

The marker pattern is built by escaping each configured marker and joining them longest-first, so `!!` wins over `!`. A marker must be followed by whitespace, which is what stops `- [ ] !important` from matching. An empty or absent `shorthand` map registers no treeprocessor at all, so the default install does no task-list rewriting.

## Error handling and migration

Every one of these raises `ValueError` when the extension loads, naming the offending key and the fix. Failing the build is correct here: all of them are silent no-ops otherwise, and all come from the site owner's own config.

| Condition | Message intent |
| --- | --- |
| `levels` present | Names the replacement, with the TOML to write instead. This is the one every 0.2.0 user hits. |
| Unknown name in `catalogue` | Lists the valid type names. |
| Unknown type key in `badges` | Lists the valid type names. |
| `shorthand` value naming a badge not in the resolved map | Says the badge is not in scope, and whether widening `catalogue` would fix it. |
| Badge value not a string, or empty | Unchanged from `review-fixes`. |

`MIGRATING.md` at the repo root covers 0.2.0 to 1.0: the package rename, the config key rename, `levels` to `badges.priority`, restoring `!` / `!!` in three lines, and the `level_rank` to `rank_of` and `LEVELS` to `catalogue_for` API moves. The 0.2.0 PyPI project keeps its final release and gets a README note pointing at the new name.

## Docs and tooling

`scripts/gen_badges.py` drops its data and becomes a renderer that imports `CATALOGUE` from the package, so the shipped catalogue and `docs/badges.md` cannot drift. Regenerating `docs/img/catalogue.png` stays a manual step, done when the catalogue changes.

The README is restructured around the new model: what a badge is, the three types, the catalogue with its image, custom badges, shorthand, then the parsing API.

## Testing

New coverage:

- Catalogue scoping: all, a subset, and the empty list.
- A user badge that adds versus one that overrides, and rank stability under override.
- Type isolation: `priority_of` ignores a status or branding badge; `badges_in` returns all three types in document order.
- The shorthand map: a single marker, a multi-character marker, longest-first precedence, no `shorthand` meaning no rewriting, and a marker that needs trailing whitespace.
- Each `ValueError` path, especially the `levels` migration error.

Kept from the existing suite, adapted to the new names: escaping, code spans, extended CSS values, contrast including the leading-colour rule and alpha hex, nested and loose task lists, bullet variants, and the uppercase checkbox.

## Release

Version goes to `1.0.0`. `pyproject.toml` changes `name` to `markdown-badges`, the wheel packages `src/markdown_badges`, and the project URLs keep pointing at the existing repository. The `CHANGELOG.md` `Unreleased` block becomes the `1.0.0` entry, with a **Removed** section listing `levels`, the built-in shorthand, and the dropped API names, and a **Changed** section for the rename. The work already on `review-fixes` is released as part of 1.0 rather than as a separate 0.3.0, since it never shipped.

## Out of scope

- A JSON export of the catalogue. Nothing consumes one; it is one command to add when something does.
- Per-badge `style` as a separate field from `color`. The extended value already covers it and adds no second syntax to learn.
- Rendering the catalogue image in CI.
- Any change to how the contrast calculation works.
